# ADR-007: Mongo Projection {_id: 0} + Application-Level UUID id + ISO 8601 Datetimes

## Status

Accepted (locked, 2026-05-10) — promoted from IMPLICIT-007.

## Context

EMITS persists every operational record (vessels, barges, trucking, biomassa, PO Batubara, merit-order, smart-stock, sumber-pemakaian, COA reconciliation, users, app_settings, ai_chat_history) in MongoDB via Motor (ADR-001). The persistence-layer contract — what the API returns, what identifier the frontend keys on, how datetimes serialize — is locked SPEC at CONS-projection-id-contract and is currently in effect across every list and detail endpoint in `backend/server.py`.

The contract has three components:

1. **Mongo `_id` is invisible.** Every `find` / `find_one` / `find_one_and_update` call uses projection `{"_id": 0}` so the bson ObjectId never crosses the API boundary. This means the API surface is independent of Mongo's internal identifier (cleaner contract, easier datastore migration if v2 ever needs it).
2. **Application-level UUID `id` is the public identifier.** Every record gets a `uuid.uuid4()` string in field `id` at insert. Frontends, tests, and exports all key on this field.
3. **Datetimes are ISO 8601 strings.** `created_at`, `updated_at`, `uploaded_at`, `umpire_completed_at` (and the audit `*_by` user-id companions) are all ISO 8601 strings on the wire. No raw `datetime` objects, no Mongo-native dates leak through.

This is in production today across 721 COA rows, 461 trucking rows, 207 smartstock rows, 301 PO Batubara rows, 111 vessels, 58 merit-order rows, 45 biomassa, plus users and ai_chat_history. The data already conforms; this ADR locks the rule so future code keeps conforming.

## Decision

All Mongo reads in EMITS MUST use projection `{"_id": 0}`. The public-facing identifier is the application-level UUID stored as a string in the `id` field, generated by `uuid.uuid4()` at insert time. All datetime fields are serialized as ISO 8601 strings (UTC) on read.

Locked clauses:

- **Projection rule:** every `db.<collection>.find(...)` / `find_one(...)` / `find_one_and_update(...)` call passes `{"_id": 0}` (or includes `_id` exclusion via the second positional arg).
- **Identifier rule:** insert path generates `id = str(uuid.uuid4())` and stores it as a string field; the frontend, exports, and lookups all use this `id` field. Mongo's `_id` is never exposed.
- **Datetime rule:** all `created_at`, `updated_at`, `uploaded_at`, `umpire_completed_at` (and any future `*_at` audit field) are stored and returned as ISO 8601 strings (e.g., `2026-05-10T14:30:00Z` or with microseconds + offset). Insert path uses `datetime.now(timezone.utc).isoformat()` or equivalent.
- **Audit metadata:** locked names — `created_at`, `updated_at`, `uploaded_at`, `umpire_completed_at` (timestamps); `created_by`, `updated_by`, `uploaded_by`, `umpire_completed_by` (user-id references to `users.id`).
- **Exception scope:** the only place `_id` is allowed near the API surface is server-internal logic (e.g., a `findOneAndUpdate(..., {"_id": ObjectId(x)})` would be rejected at code review; queries must use the application `id` field).

## Consequences

**Positive:**

- API surface is datastore-independent; `_id` (a bson ObjectId, Mongo-specific) never leaks. If v2 ever needs to migrate off Mongo (ADR-001 leaves the door explicitly open as a v2 conversation), the public contract is unchanged.
- UUIDs are universally portable: copy/paste-friendly in logs and bug reports, no collision risk across distributed inserts, no auto-increment sequence to coordinate.
- ISO 8601 datetimes are JSON-native; the frontend parses with `new Date(str)` directly; backend exports (jspdf, xlsx) format from a string source rather than a typed Date object.
- Audit metadata names are consistent across every collection — easy to reason about authorship and provenance, easy to document in DATABASE_SCHEMA.md.

**Negative / accepted tradeoffs:**

- UUIDs are 36-character strings; index size and disk footprint are non-trivial vs an integer auto-increment. Acceptable at current row counts (largest collection 721 rows).
- UUID v4 has no temporal ordering — sorting by `id` is meaningless. This is fine because every collection has a `created_at` / `time_arrival` / `periode_*` field that handles ordering. UUID v7 (timestamp-prefixed UUIDs) would give ordering for free but isn't generated by Python's stdlib `uuid.uuid4()`; retrofitting v7 across 721 COA rows + 461 trucking rows isn't worth the migration churn for v1.
- Mongo aggregations that need to JOIN by `_id` can't use the application `id` field directly without an extra step; in practice this never happens because cross-collection joins are application-layer (ADR-001 consequence).
- Every developer must remember the `{"_id": 0}` projection on new endpoints. Mitigated by code review and the established pattern across every existing list endpoint.

## Alternatives Considered

- **Expose Mongo `_id` (bson ObjectId) directly as the public identifier** — rejected. Leaks Mongo internals; changes API surface if datastore migrates; ObjectIds aren't human-friendly in logs and bug reports.
- **Auto-incrementing integer id (Postgres-style sequence)** — rejected. Mongo has no native sequence primitive that scales across replicas; would require a `counters` collection with `findOneAndUpdate({_id: collection_name}, {$inc: {seq: 1}})` on every insert, adding latency and a single-row hot spot.
- **UUID v7 (timestamp-prefixed)** — considered, rejected for v1. Would give free temporal ordering but Python stdlib's `uuid.uuid4()` generates v4; existing 1800+ records all use v4-shaped strings; not worth the migration churn. v2 conversation if ordering ever becomes a hot path.
- **Composite natural key (e.g., `shipment_code + suppliers + periode`)** — rejected. Operators occasionally re-key shipments after upload errors; a stable surrogate UUID isolates the business key from the database identity.
- **Datetimes as Mongo `Date` (BSON-native, not ISO string)** — rejected. Adds a serialization step on every read and complicates direct JSON consumption by the frontend; ISO 8601 strings are simpler at every layer.
