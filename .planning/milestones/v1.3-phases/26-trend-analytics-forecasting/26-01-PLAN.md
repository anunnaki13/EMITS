## Tasks

### Task 1 - Trend Analytics Service

Create `backend/services/trend_analytics.py`.

Implementation requirements:

- Resolve current and previous period windows for `YYYY`, `YYYY-MM`, explicit `date_from/date_to`, and `all`.
- Compute current-vs-previous metrics for stock, arrivals, supplier performance, COA deltas, and disputes.
- Return metric objects with `current`, `previous`, `delta`, `delta_percent`, `direction`, `status`, and Indonesian `label`.
- Return `supplier_trends` rows with volume, timeliness, quality delta, dispute movement, and risk label.
- Return `stock_forecast` with deterministic burn assumptions, expected arrivals, 7/14/30 day horizons, coverage days, confidence, and caveats.
- Return `sparse_data`, `confidence`, `source_counts`, and Indonesian `caveats` when historical data is limited.

Acceptance:

- Service can run directly against isolated test DB.
- No live secrets or LLM calls required.
- Messages and caveats are Indonesian.

### Task 2 - Dashboard And Report Payload Integration

Integrate the service additively into:

- `backend/services/dashboard_metrics.py`
- `backend/services/management_reports.py`

Implementation requirements:

- Add `trend_analytics` to `build_dashboard_operational(...)`.
- Add `trend_analytics` to `build_management_report(...)`.
- Preserve existing response keys and existing data-quality caveats.
- Keep computations bounded and avoid circular imports.

Acceptance:

- Existing dashboard and management report tests still pass.
- New tests assert `trend_analytics` presence and key contract fields.

### Task 3 - Management Report Exports

## Threat Model

- Do not expose secrets in trend payloads or exports.
- Avoid overconfident forecasts when burn/arrival data is missing.
- Do not block dashboards/reports if trend computation encounters sparse data.
- Keep additive contracts stable for existing frontend consumers.
- Export only summarized trend values, not raw hidden Mongo internals.
