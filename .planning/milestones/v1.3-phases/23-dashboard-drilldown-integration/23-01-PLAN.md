## Execution Tasks

### Task 1 - Shared Drilldown Contract

Create shared frontend helpers in `frontend/src/utils/dashboardDrilldown.js`.

Implementation requirements:

- Parse `from`, `period`, `supplier`, `mode`, `status`, `umpire_status`, `tab`, `date_from`, and `date_to`.
- Convert valid `YYYY` and `YYYY-MM` periods into date ranges.
- Build dashboard return URLs from original dashboard filter params.
- Build display chip metadata with Indonesian labels.
- Provide a reset helper that removes dashboard-derived params from the current route.

Acceptance:

- Direct calls with empty search strings return inactive/default state.
- Invalid period values do not throw.
- Helper output can be reused by all destination pages.

### Task 2 - Shared Drilldown UI

Create `frontend/src/components/DashboardDrilldownBar.js`.

Implementation requirements:

- Render only when dashboard context or active dashboard filters exist.
- Show `Filter dashboard aktif` plus chips for period, supplier, mode, and status.
- Include `Kembali ke dashboard` and `Reset filter dashboard`.
- Use existing design tokens/classes and responsive wrapping.
- Use icon buttons or icon+text buttons consistent with existing app libraries.

Acceptance:

- Bar fits on mobile and desktop.
- Buttons are accessible and keyboard-focusable.
- No nested card layout.

### Task 3 - Dashboard Source And Return State

Update `frontend/src/pages/Dashboard.js`.

Implementation requirements:

- Initialize dashboard filters from URL params so return navigation restores state.
- Add `from=dashboard` to all drilldown links.
- Keep current dashboard information architecture and operational cards intact.

Acceptance:

- `/dashboard?period=2026-03&supplier=X&mode=vessel` opens with matching filter selections where options exist.
- Drilldown links include active dashboard filters and source marker.

### Task 4 - Destination Page Integration

Update destination pages.

Smart Stock:

- Initialize date filters from `period` or explicit date params.
- Pass supplier to backend when supplied.
- Show drilldown bar and filtered empty state.

PO Batubara:

- Initialize year/month from `period`.
- Auto-expand selected year/month.
- Pass supplier into month fetches.
- Show drilldown bar and filtered empty state.

COA Reconciliation:

- Initialize date/status filters from dashboard params.
- Pass supplier/date/status to list, KPI, trend, and supplier calls.
- Show drilldown bar and filtered empty state.

Dispute Monitor:

- Initialize status/date/supplier context from query params.
- Pass all supported filters to backend.
- Show drilldown bar and filtered empty state.

Laporan:

- Keep existing query-based report behavior.
- Add shared drilldown bar.
- Reset dashboard params consistently.

Acceptance:

- Each destination visibly reflects active dashboard filters.
- Reset clears dashboard-derived filters and reloads unfiltered/default data.
- Direct visits without query params still work.

### Task 5 - Backend Filter Support

Update backend endpoints as needed.

Implementation requirements:

- Add supplier/date/status filters to COA endpoints using one shared backend filter builder.
- Add supplier support to smart stock endpoint without unsafe dynamic Mongo field queries.
- Keep PO and reports behavior backward compatible.
- Escape or normalize user-provided text filters before regex matching.

Acceptance:

- Existing unfiltered endpoint responses remain backward compatible.
- Filtered payloads are internally consistent across list and summary endpoints.
- Malformed query params return safe default/no-match behavior, not server errors.

## Threat Model

- URL query params are untrusted input.
- Supplier/status filters must not be interpolated into unsafe regexes or dynamic DB paths without escaping/validation.
- Reset/back URLs must not allow open redirects; return target is always local `/dashboard`.
- Filter failures must not expose stack traces or secrets.
