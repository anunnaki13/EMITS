Phase 1 audit confirmed the backend is healthy at the API layer (login 200/401, register 200/400, /me 200/401) but flagged TWO contract divergences from CONS-auth-header:

1. **422→400** (must reconcile): malformed login/register body returns 422 (FastAPI Pydantic default); CONS-auth-header says 400. **Decision (made here, not deferred):** add a custom `RequestValidationError` handler that re-emits 400 for paths under `/api/auth/`. Rationale: (a) CONS-auth-header is locked SPEC and downstream documentation expects 400; (b) scoping the handler to `/api/auth/` only is a one-line conditional that does not disturb other routes (vessels/COA/etc. keep FastAPI's 422 default — those routes are not part of the locked contract); (c) frontend toast handler at Login.js:37 reads `error.response?.data?.detail` which works for both 400 and 422 (no FE break); (d) regression test pinpoints the change.

2. **401-vs-403** for missing-credentials (accept as-is, document): FastAPI's `HTTPBearer` raises 403 when no Authorization header is sent and 401 when a token is present-but-invalid. CONS-auth-header says 401 for "invalid/expired token" — which IS what's shipping. The 403-on-missing-header is FastAPI's documented default for this security class; tests verify both paths separately. **Decision: keep 403 for missing-header path; document as the actual contract.** Rationale: changing it requires overriding the security dependency, which has cross-route blast radius (every protected endpoint).

Tests live in `backend/tests/test_auth_session.py` and use a new `conftest.py` to source credentials from env vars (per CREDENTIAL_HYGIENE.md from Plan 02-01) and to clean up the 3 `audit-probe-*` synthetic users left over from Phase 1 plan 01-04.
